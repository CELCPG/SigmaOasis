WHAT YOU ARE DOING

You are judging two captured runs of a desktop AI chat application, blind. Two
builds of the same application were given identical prompts, identical fixtures,

================================================================
THE RULE THAT MATTERS MOST
================================================================

Both runs used the SAME local model with the SAME prompt. Any difference in how
knowledgeable, complete, accurate, or well-written the ANSWER is, is model
sampling variance. It is not a property of the application and it is never a
reason to pick a winner.

You are judging the APPLICATION: what it displays, what it records, what
controls it offers, how long it takes, how it lays out, and what it says about
its own behaviour.

Before writing any WINNER, ask yourself: "would this difference still be here if
the model had emitted identical tokens in both runs?" If the answer is no — if
the difference is only in the model's wording, its choice of facts, or how much
it happened to say — the answer is `tie`.

Never reward the run whose answer is more knowledgeable, more detailed, better
written, or more correct about the world. A run whose answer is factually wrong
can win. A run whose answer is excellent can lose.

================================================================
TIES ARE REAL
================================================================

`tie` is a real answer and is often the correct one. Score `tie` when:

- both runs behave the same way on the task's question, even if both behave badly;
  - neither run was actually put to the test — the situation the task sets up
  did not arise, the model did not emit the thing the task measures, or the
  driver action the task depends on did not land. A task where neither build was
  tested is a TIE, not a coin flip;
- the only differences you can find are in the model's wording;
- the artifacts you need are missing or empty in one or both runs.

Do NOT break a tie on something incidental: response length, a nicer sentence,
one run being marginally faster on a quantity this task does not ask about.

================================================================
WHAT IS IN A RUN DIRECTORY
================================================================

- transcript.json    every message and every tool-call record (name, args,
                     result, status), plus the turn's trace export.
- reply.md           the final assistant message as RAW MARKDOWN — exactly what
                     the model emitted, before rendering.
- reply.txt          the rendered innerText — WHAT THE READER ACTUALLY SAW on
                     screen. A collapsed block contributes only its header here.
                     Diffing reply.md against reply.txt is how you separate
                     "the model wrote it that way" from "the app drew it that
                     way": a character present in reply.md and absent from
                     reply.txt was lost by the renderer.
- messages-raw.json  { index, role, content, reasoning } per message.
- dom/               outerHTML of the assistant message and of any plan block,
                     captured at the moments the task names.
- snapshots/         DOM captured at named moments, plus keyboard-traversal
                     records where a task collected them.
- timings.json       t0 (the Enter keydown) and every marked timestamp.
- styles.json        computed styles for the nodes the visual tasks measure, in
                     both themes.
- fixtures/ or fixture.log   every request each loopback fixture served.
- trace/audit.jsonl  the exported session audit log, for tasks that enable it.
- shots/             screenshots, taken only after any timed window closed.
- run.json           driverActions, turns, setup.seededSettingsVerified,
                     preconditions, validity, auditExport.

Not every run has every file. An empty reply.md with `run.json →
rawMarkdown.error` set is a known artifact gap, not a defect of the build.

Check `run.json → validity` and `run.json → preconditions` before concluding
anything. If a run is invalid or a precondition did not hold, say so and score
the task `tie` unless the other run's evidence stands entirely on its own.

## V1
----------------------------------------------------------------

THE QUESTION: Of the quantities each answer states, how accurately does the
screen represent which of them the retrieved text supports?

MEASURE AND REPORT FOR BOTH RUNS:

1. Every tool record for this turn — name, status, full result text. Report
   the count and the statuses for both runs, even when they are identical.
2. Every numeric quantity with a unit that the answer states. List them and
   report the count for both runs.
3. For each quantity, whether that value occurs in the captured tool result
   text. Report the SUPPORTED and NOT-FOUND counts per run.
4. For each NOT-FOUND quantity, what the reader is told about it — answer
   prose, a label, a marker, a provenance line, anything at all. Quote it, or
   write nothing.
5. The reverse direction: any quantity a run presents as uncertain,
   unsupported or unverified that the retrieved text does contain. Report that
   count too, including when it is zero.
6. Whether the retrieved passage text is legible on screen at all, or exists
   only in the transcript — that is, whether a reader could have checked any of
   this without the artifacts.

HOW TO DECIDE: The run whose on-screen picture of which quantities are backed
matches its own record more closely. A quantity left unmarked and a quantity
marked wrongly are both mismatches and both count. Stating fewer quantities is
not itself better, so report the stated count beside the mismatch count. If the
two runs state different quantities only because the model sampled differently,
that is not a difference — say so. If neither run stated an unsupported
quantity, the marking behaviour was never exercised in either; report that
rather than deciding on it.

## V2
----------------------------------------------------------------

THE QUESTION: Of the citations each reply puts in front of the reader, how many
can the reader follow to the cited text, and in how many interactions?

MEASURE AND REPORT FOR BOTH RUNS:

1. The count of bracketed citation markers in the raw markdown and,
   separately, in the rendered text. Report both numbers and any difference
   between them — that difference is what the renderer did to them.
2. Every element inside the assistant message a reader could activate to
   reach a cited document. List their visible text or accessible names and give
   the count for both runs.
3. Whether the retrieved passage text itself appears anywhere in the rendered
   message, or only in the transcript.
4. Any source or provenance listing present: quote it verbatim, and state
   what kind of element each source name sits in and whether that element does
   anything when activated.
5. Where the run recorded an activation of such a control, what changed as a
   result, and how long it took.

HOW TO DECIDE: Decide on the gap between offered and reachable, reported as a
pair for both runs. A run with several markers and no route to any of them, and
a run with no markers and no routes, are not the same thing: the second offers
nothing it cannot honour, and the pair shows that. A route that leads somewhere
other than the cited passage counts as offered-and-unreachable. If the marker
counts differ only because the model wrote a different number of them, say so
and weigh reachability instead.

## V3
----------------------------------------------------------------

THE QUESTION: How closely does each message’s account of where its figures came
from match what that run actually did?

MEASURE AND REPORT FOR BOTH RUNS:

1. Every tool record for this turn and its status, from the transcript and
   from the exported audit where present. The count may legitimately be zero —
   report the number either way, for both runs.
2. Whether any provenance line, source list or tool-call block is displayed
   to the reader. Quote it, or write none.
3. Every water-volume figure and every currency figure the answer states.
   List them and give the count.
4. Every sentence in the message that says or implies anything about where
   the figures came from — any claim of having checked, consulted, searched or
   looked something up, and any hedge. Quote them, or write none.
5. The mismatch in both directions: figures presented as grounded that
   nothing in the record grounds; any claim of consultation the record does not
   show; and any consultation that did happen and the message never mentions.
   Report all three counts.

HOW TO DECIDE: The run whose on-screen account best matches its own record.
Consulting nothing and saying nothing about it is a different failure from
consulting nothing and saying it checked — report which one is in front of you
rather than merging them. Over-claiming counts at least as heavily as silence.
Saying less is not automatically better, so report the figure count alongside.
If both runs consulted the same thing, including nothing, and both say the same
about it, that is a tie.

## TH1
----------------------------------------------------------------

THE QUESTION: Could a reader, from the message alone, correctly state which
tools ran on this turn?

MEASURE AND REPORT FOR BOTH RUNS:

1. EXECUTED — from the transcript and the exported audit: every tool name
   invoked this turn and its status. Give the set and the count. Report the
   audit’s entry count and whether its hash chain verified, or say it is absent.
2. SHOWN — from the rendered message and its markup: every tool call visible,
   by name. Give the set and the count, and note which are readable without
   interaction.
3. CLAIMED — from the raw markdown: every statement the answer makes about
   its own process, quoted. Include explicit tool names and phrases that name no
   tool, such as claims of having searched, looked something up, checked or used
   something.
4. Three counts per run: how many CLAIMED are not in EXECUTED; how many
   EXECUTED are not in SHOWN; how many EXECUTED the answer’s own account omits.
5. Anything in the message that addresses a mismatch, quoted, or nothing.

HOW TO DECIDE: The run where the reader’s achievable picture of tool use matches
that run’s own record. Naming a tool that did not run and hiding a tool that did
both count against. If neither reply made a process claim, the claim side was
not exercised in either run — say so and decide on visibility alone, or tie if
that matches too. Do not credit a run for a reply that happened to be modest.

## TH2
----------------------------------------------------------------

THE QUESTION: How accurately does each message represent whether the lookup
succeeded and where its links came from?

MEASURE AND REPORT FOR BOTH RUNS:

1. The search record — name, status, and result or error text, quoted. From
   the fixture log: how many requests it served and what it returned. If a run’s
   record is not an error, say so plainly: the task’s premise may not have held
   there.
2. The count of URLs in the raw markdown and, separately, in the rendered
   text. Report both, and list any URL present in one and absent from the other.
3. For each URL, whether it appears verbatim in the output of any record that
   completed this turn. Report the SUPPORTED and NOT-FOUND counts.
4. Whatever the message says about the lookup itself — that it worked, that

5. Whether a tool-call block for the lookup is visible to the reader and what

HOW TO DECIDE: Whether the picture the message gives matches the record, on both
halves: the failure and the links. A run that emitted no URLs was not tested on
the link half — note it and decide on the failure half. Report both counts for
both runs even when they are zero, and never decide on the model’s raw URL
count.

## TH3
----------------------------------------------------------------

THE QUESTION: Would a reader who trusts this message — its quotation marks and
its statements about its own retrieval — be reading something the record
supports?

MEASURE AND REPORT FOR BOTH RUNS:

1. The retrieval record: its status, the documents it returned by name, and
   the full retrieved text.
2. Every span the reply presents as a quotation, from the raw markdown. Give
   the count and list them.
3. For each, whether it occurs as a contiguous substring of the retrieved
   text once whitespace and case are normalised. Report the EXACT and NOT-FOUND
   counts. For each NOT-FOUND, set the reply’s version and the closest retrieved
   text side by side so the difference is visible.
4. The document each quotation is attributed to, and whether that document is
   in the retrieved set.
5. Every statement the application itself makes on this screen about the
   retrieval — how many documents were consulted, any claim about whether the
   answer is backed by them, any passage marked as used or cited, any provenance
   line, any badge. Quote each and report how many there are.
6. Whether any two of those statements disagree with each other, and whether
   any of them disagrees with the record. Report the count of disagreements for
   both runs, including zero.
7. Whether the retrieved text was readable on screen, or existed only in the
   transcript.

HOW TO DECIDE: Whether the screen lets a reader tell a faithful quotation from
an invented one, and whether the screen agrees with itself about what was
retrieved. Report both counts — quotations not found, statements that disagree —
for both runs, including zero and zero, which is a tie. If both runs quoted
accurately the quotation half was never exercised: say so and decide on the
consistency half, or tie if that matches too. Do not credit a run for quoting
more gracefully; credit only what the application did with the quotation.
