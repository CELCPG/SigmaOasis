WHAT YOU ARE DOING
================================================================

You are judging two captured runs of a desktop AI chat application, blind. Two
builds of the same application were given identical prompts, identical fixtures,
the same machine, and the same local model. You are not told which build
produced which run. There is no order guarantee: `run-1` may be either build,
and it may be a different build from one task to the next. Treat every task
independently.

================================================================
THE RULE THAT MATTERS MOST
================================================================

Both runs used the SAME local model with the SAME prompt. Any difference in how
knowledgeable, complete, accurate, or well-written the ANSWER is, is model
sampling variance. It is not a property of the application and it is never a
reason to pick a winner.

You are judging the APPLICATION: what it displays, what it records, what
controls it offers, how long it takes, how it lays out, and what it says about
its own behaviour.

Before writing any WINNER, ask yourself: "would this difference still be here if
the model had emitted identical tokens in both runs?" If the answer is no — if
the difference is only in the model's wording, its choice of facts, or how much
it happened to say — the answer is `tie`.

This batch contains timing tasks, so one specific trap needs naming: a run whose
model emitted FEWER TOKENS will finish sooner, and that is not the application
being faster. Before you use any total-completion number, compare the length of
reply.md in the two runs. If one reply is materially longer, say so and do not
decide the task on completion time.

Never reward the run whose answer is more knowledgeable, more detailed, better
written, or more correct about the world.

================================================================
TIES ARE REAL
================================================================

`tie` is a real answer and is often the correct one. Score `tie` when:

- both runs behave the same way on the task's question, even if both behave badly;
- neither run was actually put to the test — the situation the task sets up did
  not arise, or the driver action the task depends on did not land. A task where
  neither build was tested is a TIE, not a coin flip;
- the only differences you can find are in the model's wording or its output
  length;
- the artifacts you need are missing or empty in one or both runs.

Do NOT break a tie on something incidental: response length, a nicer sentence,
or a difference in a measurement this task does not ask about. On timings, treat
differences that are small relative to the wait being measured as noise, and say
so rather than picking a winner from them.

================================================================
WHAT IS IN A RUN DIRECTORY
================================================================

- transcript.json    every message and every tool-call record (name, args,
                     result, status), plus the turn's trace export.
- reply.md           the final assistant message as RAW MARKDOWN — exactly what
                     the model emitted, before rendering.
- reply.txt          the rendered innerText — WHAT THE READER ACTUALLY SAW on
                     screen. A collapsed block contributes only its header here.
                     Diffing reply.md against reply.txt is how you separate
                     "the model wrote it that way" from "the app drew it that
                     way": a character present in reply.md and absent from
                     reply.txt was lost by the renderer. This diff is the
                     central tool for VC1.
- messages-raw.json  { index, role, content, reasoning } per message.
- dom/               outerHTML of the assistant message and of any plan block,
                     captured at the moments the task names.
- snapshots/         DOM captured at named moments, plus keyboard-traversal
                     records where a task collected them.
- timings.json       t0 (the Enter keydown) and every marked timestamp.
- styles.json        computed styles for the nodes the visual tasks measure, in
                     both themes.
- fixtures/ or fixture.log   every request each loopback fixture served.
- trace/audit.jsonl  the exported session audit log, for tasks that enable it.
- shots/             screenshots, taken only after any timed window closed.
                     Note that no screenshots are taken inside a timed window,
                     by design — so for the timing tasks the evidence of what
                     was on screen during a wait is in dom/, snapshots/ and
                     timings.json, not in shots/.
- run.json           driverActions, turns, setup.seededSettingsVerified,
                     preconditions, validity, auditExport.

Not every run has every file. An empty reply.md with `run.json →
rawMarkdown.error` set is a known artifact gap, not a defect of the build.

Check `run.json → validity` and `run.json → preconditions` before concluding
anything. If a run is invalid or a precondition did not hold, say so and score
the task `tie` unless the other run's evidence stands entirely on its own.

## TTU1
----------------------------------------------------------------

THE QUESTION: How long is the screen without readable content, and what occupies
it during that time?

MEASURE AND REPORT FOR BOTH RUNS:

1. From fixtures/: how many times the search fixture was hit and what latency it
   served. Report the numbers for both runs. If a run hit it a different number
   of times, or was served a different latency, the two runs are not comparable
   — say so plainly.
2. From timings.json, in ms from t0: the time of the first non-whitespace text
   in the assistant message body, and the time of the last content mutation.
   Give both numbers for both runs.
3. What was on screen between t0 and the first text. Quote any text present in
   the dom/ or snapshots/ captures taken in that interval. If the only thing
   present was an indicator with no text, say so and quote the element.
4. Whether a Stop control existed and was enabled during that interval, with the
   timestamped evidence.
5. The character length of reply.md in each run, so completion time can be
   interpreted.

HOW TO DECIDE: Report both time-to-first-readable-content numbers and both
descriptions of the wait state, then decide on which run puts readable content
in front of the reader sooner AND accounts for the wait. If the times are close
relative to the length of the wait, and the wait states are equivalent, that is
a tie. Do not decide on total completion time if the difference there tracks how
many tokens the model emitted — check the reply lengths from step 5 first.

## TTU2
----------------------------------------------------------------

THE QUESTION: How long does the reader wait on the first Python run of a
session, and what does the screen say the wait is for?

MEASURE AND REPORT FOR BOTH RUNS:

1. From run.json → preconditions: whether the runtime was present and cold and
   the app freshly launched, in each run. If a precondition did not hold in a
   run, say so — the comparison may not stand.
2. From timings.json, in ms from t0: the first appearance of the Python
   tool-call block; the first non-whitespace text in the message body; the last
   content mutation. Give all three for both runs.
3. If the run captured a warm repeat (run.json → turns), its completion time and
   the cold/warm ratio, for both runs.
4. Quote whatever text the tool block displayed while its status was running,
   from dom/ or snapshots/. If it displayed only a glyph with no words, quote
   the glyph and say there was no label.
5. Whether the block's displayed status changed over the course of the wait, and
   what each displayed string was.

HOW TO DECIDE: Report both sets of durations and both sets of displayed strings.
The boot wait itself may be effectively identical in the two runs — that is a
legitimate finding, and then the question is what the screen said during it. If
both runs show equivalent strings and comparable durations, tie. Do not credit a
run for finishing sooner if the reason is that the model wrote less code or
fewer words — compare reply.md lengths before using any duration.

## TTU3
----------------------------------------------------------------

THE QUESTION: After the answer is complete on screen, how long before the reader
can act on it, and is the delay accounted for?

MEASURE AND REPORT FOR BOTH RUNS:

1. From timings.json: the timestamp of the last mutation that appended text to
   the message body; the first timestamp at which a Copy affordance exists on
   that message; the same for a Regenerate affordance; the moment the composer
   became sendable again. Express each as a delta in ms from the answer
   finishing, and give every number for both runs.
2. From dom/ or snapshots/ captured inside that interval: quote anything
   displayed in or near the message during the gap — a status line, a label, a
   progress indicator. If nothing was displayed, write "nothing".
3. What the run's own record shows happened after the answer finished
   (transcript.json, run.json → turns) and how long it took.
4. The final message's visible text length, and whether reply.md and reply.txt
   agree on the content.

HOW TO DECIDE: The run with the shorter interval during which a finished answer
cannot be acted on; or, where the intervals are comparable, the run that
accounts for that interval on screen. Report both numbers even if they are
identical. If the gap differs mainly because one run's post-answer work had more
text to process, say so and weigh the on-screen account rather than the raw
duration.

## VC1
----------------------------------------------------------------

THE QUESTION: At each captured viewport width, does the message stay inside the
chat column, and is the full string still present and selectable?

MEASURE AND REPORT FOR BOTH RUNS:

1. From the captured layout measurements (styles.json, snapshots/, run.json),
   per width captured (1280, 900, and split view where present):
   - documentElement scrollWidth versus clientWidth;
   - the chat scroll container's scrollWidth versus clientWidth;
   - each token-bearing bubble's scrollWidth versus clientWidth;
   - each bubble's right edge versus the chat column's right edge.
   Report the NUMBERS for both runs, not a verdict.
2. Which widths, if any, exceed their container in each run.
3. Whether the full string is present in the DOM text of the user bubble and of
   the assistant bubble, and its character count in each. Compare against the
   string in the task's `prompt` in tasks-for-critics.json.
4. Compare reply.md against reply.txt for the string: characters present in the
   markdown and absent from the rendered text were dropped by the renderer —
   report exactly what was dropped, if anything.
5. What shots/ shows at each width, if screenshots exist.

HOW TO DECIDE: Overflow at any captured width counts against a run. But so does
keeping the layout intact by removing or truncating the string: a bubble that
fits because it no longer contains all the characters has failed the other half
of the question. Report both properties for both runs before deciding. If both
runs overflow identically, or both hold identically, tie.

## VC2
----------------------------------------------------------------

THE QUESTION: Following the application's own instructions with the keyboard
only, at how many Tab stops is the focused element visually indistinguishable
from its unfocused state?

MEASURE AND REPORT FOR BOTH RUNS:

1. From snapshots/ traversal records and styles.json, per theme (light and
   dark): the total number of Tab stops recorded, and for each stop whether the
   focused element's computed outline, box-shadow, border colour or background
   differs from that same element unfocused. Report the differing values, or
   state "identical".
2. Per run and per theme: N_stops, N_with_no_measurable_difference, and that as
   a PROPORTION. The two runs may have traversed different numbers of stops
   because the model's answer named a different route — normalise before
   comparing, and say what you normalised.
3. Whether every focused element's bounding rectangle intersects the viewport;
   list any stop where it does not, per run.
4. Whether the traversal actually reached the two settings the answer named, and
   the number of Tab presses to each. If a run's traversal never reached them,
   say so — its stop counts are not directly comparable to the other run's.
5. Quote each run's own instructions from reply.txt, since those determine the
   route that was walked.

HOW TO DECIDE: Decide on the proportion of Tab stops with no measurable visual
focus change, reported for both runs in both themes. If the two routes differ
enough that the sets of elements traversed are not comparable, say so and
consider a tie. If both runs show equivalent proportions, tie. Do not credit a
run for giving clearer directions — that is the model's wording, not the
application.

## VC3
----------------------------------------------------------------

THE QUESTION: How much of the last reply's prose falls below the legibility
threshold, and how far below, in each theme?

MEASURE AND REPORT FOR BOTH RUNS:

1. From styles.json, per theme: the number of prose text nodes measured, and for
   each its computed colour, its effective background, its font size and weight,
   and its contrast ratio. Report N_measured, N_below_threshold (below 4.5:1, or
   below 3.0:1 for text at or above 18.66px bold / 24px unbold), and MIN_RATIO
   together with the element it belongs to.
2. By name, the ratio of the library/provenance line if the run has one, and the
   ratio of the timing/stats readout if the run has one.
3. IMPORTANT, report explicitly: whether each of those lines EXISTS in each run.
   A run with no provenance line has no low-contrast provenance line — that is
   an absence of information, not better legibility. State which situation you
   are looking at, quoting reply.txt.
4. All of the same numbers for the other theme.

HOW TO DECIDE: Compare N_below_threshold as a PROPORTION of N_measured, and
compare MIN_RATIO, per theme, for both runs. If one run has fewer failing nodes
because it renders fewer nodes, say so explicitly, weigh legibility per node,
and put the missing content in BIGGEST REMAINING GAP. If the ratios are
equivalent in both runs, tie.
