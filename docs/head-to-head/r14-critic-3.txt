================================================================
THE RULE THAT MATTERS MOST
================================================================

Both runs used the SAME local model with the SAME prompt. Any difference in how
knowledgeable, complete, accurate, or well-written the ANSWER is, is model
sampling variance. It is not a property of the application and it is never a
reason to pick a winner.

You are judging the APPLICATION: what it displays, what it records, what
controls it offers, how long it takes, how it lays out, and what it says about
its own behaviour.

Before writing any WINNER, ask yourself: "would this difference still be here if
the model had emitted identical tokens in both runs?" If the answer is no — if
the difference is only in the model's wording, its choice of facts, or how much
it happened to say — the answer is `tie`.

Never reward the run whose answer is more knowledgeable, more detailed, better
written, or more correct about the world. A run whose answer is factually wrong
can win. A run whose answer is excellent can lose.

This batch contains timing tasks, so one specific trap needs naming: a run whose
model emitted FEWER TOKENS will finish sooner, and that is not the application
being faster. Before you use any total-completion number, compare the length of
reply.md in the two runs. If one reply is materially longer, say so and do not
decide the task on completion time.

================================================================
TIES ARE REAL
================================================================

`tie` is a real answer and is often the correct one. Score `tie` when:

- both runs behave the same way on the task's question, even if both behave badly;
  - neither run was actually put to the test — the situation the task sets up
  did not arise, the model did not emit the thing the task measures, or the
  driver action the task depends on did not land. A task where neither build was
  tested is a TIE, not a coin flip;
- the only differences you can find are in the model's wording;
- the artifacts you need are missing or empty in one or both runs.

Do NOT break a tie on something incidental: response length, a nicer sentence,
one run being marginally faster on a quantity this task does not ask about.

================================================================
WHAT IS IN A RUN DIRECTORY
================================================================

- transcript.json    every message and every tool-call record (name, args,
                     result, status), plus the turn's trace export.
- reply.md           the final assistant message as RAW MARKDOWN — exactly what
                     the model emitted, before rendering.
- reply.txt          the rendered innerText — WHAT THE READER ACTUALLY SAW on
                     screen. A collapsed block contributes only its header here.
                     Diffing reply.md against reply.txt is how you separate
                     "the model wrote it that way" from "the app drew it that
                     way": a character present in reply.md and absent from
                     reply.txt was lost by the renderer.
- messages-raw.json  { index, role, content, reasoning } per message.
- dom/               outerHTML of the assistant message and of any plan block,
                     captured at the moments the task names.
- snapshots/         DOM captured at named moments, plus keyboard-traversal
                     records where a task collected them.
- timings.json       t0 (the Enter keydown) and every marked timestamp.
- styles.json        computed styles for the nodes the visual tasks measure, in
                     both themes.
- fixtures/ or fixture.log   every request each loopback fixture served.
- trace/audit.jsonl  the exported session audit log, for tasks that enable it.
- shots/             screenshots, taken only after any timed window closed.
- run.json           driverActions, turns, setup.seededSettingsVerified,
                     preconditions, validity, auditExport.

Not every run has every file. An empty reply.md with `run.json →
rawMarkdown.error` set is a known artifact gap, not a defect of the build.

Check `run.json → validity` and `run.json → preconditions` before concluding
anything. If a run is invalid or a precondition did not hold, say so and score
the task `tie` unless the other run's evidence stands entirely on its own.

## TTU1
----------------------------------------------------------------

THE QUESTION: Between the keypress and the first useful words, how long is the
screen unhelpful, and what does it hold?

MEASURE AND REPORT FOR BOTH RUNS:

1. From the timings: the keypress, the first non-whitespace content in the
   answer, and the last content change. Report both intervals as numbers for
   both runs.
2. What occupies the screen during the first interval. Quote any label; if it
   was an unlabelled indicator, say so; if it was nothing, say that.
3. Whether the reader could abandon the wait — whether a stop control existed
   and was enabled, and from when.
4. Whether anything readable appeared before the lookup returned, and whether
   it bore on the question asked.
5. From the fixture log: how many requests were served and how long the
   fixture itself took, in both runs. If those differ, the two intervals are not
   comparable — say so.

HOW TO DECIDE: Report the intervals as numbers for both runs, then decide on
what the reader had during them. A shorter interval that shows nothing and a
longer one that names the wait are different results; report both rather than
ranking on elapsed time alone. A difference in the fixture’s own latency is a
difference in the fixture, not in the application.

## TTU2
----------------------------------------------------------------

THE QUESTION: During a wait whose reason the application knows, what does the
reader learn, and how long does it last?

MEASURE AND REPORT FOR BOTH RUNS:

1. From the timings: the keypress, the first appearance of the code block,
   the first content in the answer, and the last change. Report every interval
   for both runs.
2. The label the block carries while it is running. Quote it; if it was an
   unlabelled indicator, say so.
3. Whether anything on screen distinguishes this first, slow call from a
   later fast one. Quote it, or write nothing.
4. The warm repetition’s interval, and the cold-to-warm ratio for both runs.
5. Whether the sandbox runtime was actually present — check the run’s
   recorded preconditions. If it was absent, that run measured a failure rather
   than a start-up, and nothing about the wait can be concluded from it.

HOW TO DECIDE: Report the cold interval, the warm interval and the ratio for
both runs, then decide on what was said during the cold one. The question is
whether the application explains the wait, not whether the wait is short: a run
that is slower and says why and a run that is faster and silent are different
results, and both numbers belong in the report.

## TTU3
----------------------------------------------------------------

THE QUESTION: After the answer is complete on screen, how long before a reader
can act on it, and does anything explain the wait?

MEASURE AND REPORT FOR BOTH RUNS:

1. From the timings: the last change to the answer text; the first moment a
   copy affordance exists; the first moment a regenerate affordance exists; the
   first moment the composer accepts input again. Report each gap for both runs.
2. What the message shows during the gap. Quote any progress line, or state
   that there was none.
3. Whether the answer’s content changed after the gap began — that is,
   whether the wait produced anything the reader can see. Quote whatever
   appeared.
4. Whether the controls, once present, were enabled, and whether any of them
   was present but inert.
5. Whether both runs actually took the long path. If one finished immediately
   it was not put to the test — say so.

HOW TO DECIDE: Report the gaps as numbers for both runs. A shorter gap and an
explained gap are both good and they are not the same thing, so report both. A
gap that produced a visible result is different from one that produced nothing,
so weigh what the reader got for the wait as well as the wait.

## VC1
----------------------------------------------------------------

THE QUESTION: At each width, does the message stay inside the layout, and does
the string stay readable and recoverable?

MEASURE AND REPORT FOR BOTH RUNS:

1. At every captured width and view: whether the page scrolls sideways;
   whether the chat container scrolls sideways; whether each token-bearing
   bubble exceeds its own width; and where each bubble’s right edge falls
   against the chat column’s. Report the numbers for both runs at every width,
   not a verdict.
2. Which widths, if any, exceed their container in each run.
3. Whether the whole string is present in the message text of the reader’s
   bubble and of the reply, character for character. Report the length found
   against the length sent.
4. How the string is broken across lines on screen. Quote a wrapped line as
   rendered, and state whether any character was introduced at a break — that
   is, whether a reader transcribing from the screen would reproduce the string
   exactly.
5. Whether the string is still selectable and copyable as one run of text,
   and whether anything shortens it for display in a way that also shortens what
   can be copied.

HOW TO DECIDE: Report the width-by-width geometry for both runs, then the
string’s integrity, then decide. Holding the layout by dropping characters, or
by introducing one at every break, is not a better result than overflowing —
report both halves so that a trade shows up as a trade. If both runs overflow
identically, or both hold identically, that is a tie.

## VC2
----------------------------------------------------------------

THE QUESTION: Following the application’s own instructions with the keyboard,
how many stops leave the reader unable to see where they are?

MEASURE AND REPORT FOR BOTH RUNS:

1. The number of stops traversed on each route, for both runs and both
   themes.
2. Per stop, whether the focused state differs visibly from the unfocused one
   and by what property. Report the count of stops with a visible difference and
   the count without, per theme, per run.
3. Per stop, whether the focused element is on screen and whether anything is
   covering it. Report the count of stops that take focus while obscured.
4. Whether the route actually reaches both settings the answer names, and how
   many stops that took.
5. Whether the two runs traversed routes of the same length. If the two
   answers named different destinations, the traversals are not directly
   comparable — say so and compare proportions.

HOW TO DECIDE: Report, per run and per theme: stops traversed, stops with no
visible focus change, stops obscured. Read them as proportions, since a shorter
route is not itself better. A run that hides fewer stops in one theme and more
in the other has not won; report both themes separately and say so.

## VC3
----------------------------------------------------------------

THE QUESTION: How legible is the application’s own account of what it did, in
each theme?

MEASURE AND REPORT FOR BOTH RUNS:

1. For every text node in the last reply long enough to read: its contrast
   ratio against its effective background, with any transparency composited.
   Report the number of nodes measured, the number below the WCAG AA threshold
   for their size and weight, and the worst ratio found — per theme, per run.
2. The same three numbers, named, for the provenance line and for the timing
   readout specifically.
3. The font size and weight of each of those two lines, since the applicable
   threshold depends on them.
4. Whether both runs had the same lines to measure. If a run has no
   provenance line at all, say so: an absent line has no ratio, and the runs are
   not comparable on it.
5. Any text below the threshold in one theme and above it in the other. Name
   it.

HOW TO DECIDE: Report the three numbers per theme per run. Fewer nodes below
threshold is better, and so is a higher worst case. A run with fewer failing
nodes because it printed less prose is not thereby better, so report the node
count alongside. If a line the task names is missing from one run, that is a
difference in what was said and not in how legible it was; report it apart from
the ratios.
