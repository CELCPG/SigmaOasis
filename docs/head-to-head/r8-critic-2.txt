WHAT YOU ARE DOING

You are judging two captured runs of a desktop AI chat application, blind. Two
builds of the same application were given identical prompts, identical fixtures,
the same machine, and the same local model. You are not told which build
produced which run. There is no order guarantee: `run-1` may be either build,

================================================================
THE RULE THAT MATTERS MOST
================================================================

Both runs used the SAME local model with the SAME prompt. Any difference in how
knowledgeable, complete, accurate, or well-written the ANSWER is, is model
sampling variance. It is not a property of the application and it is never a
reason to pick a winner.

You are judging the APPLICATION: what it displays, what it records, what
controls it offers, how long it takes, how it lays out, and what it says about
its own behaviour.

Before writing any WINNER, ask yourself: "would this difference still be here if
the model had emitted identical tokens in both runs?" If the answer is no — if
the difference is only in the model's wording, its choice of facts, or how much
it happened to say — the answer is `tie`.

Never reward the run whose answer is more knowledgeable, more detailed, better
written, or more correct about the world. A run whose answer is factually wrong
can win. A run whose answer is excellent can lose.

================================================================
TIES ARE REAL
================================================================

`tie` is a real answer and is often the correct one. Score `tie` when:

- both runs behave the same way on the task's question, even if both behave badly;
- neither run was actually put to the test — the situation the task sets up did
  not arise, or the driver action the task depends on did not land. A task where
  neither build was tested is a TIE, not a coin flip;
- the only differences you can find are in the model's wording;
- the artifacts you need are missing or empty in one or both runs.

Do NOT break a tie on something incidental: response length, a nicer sentence,
one run being marginally faster on a quantity this task does not ask about.

WHAT IS IN A RUN DIRECTORY
================================================================

- transcript.json    every message and every tool-call record (name, args,
                     result, status), plus the turn's trace export.
- reply.md           the final assistant message as RAW MARKDOWN — exactly what
                     the model emitted, before rendering.
- reply.txt          the rendered innerText — WHAT THE READER ACTUALLY SAW on
                     screen. A collapsed block contributes only its header here.
                     Diffing reply.md against reply.txt is how you separate
                     "the model wrote it that way" from "the app drew it that
                     way": a character present in reply.md and absent from
                     reply.txt was lost by the renderer.
- messages-raw.json  { index, role, content, reasoning } per message.
- dom/               outerHTML of the assistant message and of any plan block,
                     captured at the moments the task names.
- snapshots/         DOM captured at named moments, plus keyboard-traversal

- timings.json       t0 (the Enter keydown) and every marked timestamp.
- styles.json        computed styles for the nodes the visual tasks measure, in
                     both themes.
- fixtures/ or fixture.log   every request each loopback fixture served.
- trace/audit.jsonl  the exported session audit log, for tasks that enable it.
- shots/             screenshots, taken only after any timed window closed.
- run.json           driverActions, turns, setup.seededSettingsVerified,
                     preconditions, validity, auditExport.

Not every run has every file. An empty reply.md with `run.json →
rawMarkdown.error` set is a known artifact gap, not a defect of the build.

Check `run.json → validity` and `run.json → preconditions` before concluding

## PT1
----------------------------------------------------------------

THE QUESTION: How much of what the plan actually did can the person who approved
it see?

MEASURE AND REPORT FOR BOTH RUNS:

1. EXECUTED — from transcript.json and trace/audit.jsonl: every tool invocation
   that occurred during the plan turn, with name, arguments and status. Give the
   total count and the set of distinct names. Also report run.json →
   auditExport (entry count, hash chain verified); if the audit was not exported
   for a run, say so, because it bounds what you can conclude about that run.
2. VISIBLE — from reply.txt and dom/: every tool-call block present anywhere in
   the message or plan block, by name. Report two numbers: how many are present
   in reply.txt (on screen without any interaction) and how many are present in
   the dom/ capture at all (reachable by expanding).
3. The set difference in BOTH directions, with counts: executed-but-absent from
   the message, and shown-but-not-executed.
4. For each visible call, whether its arguments and its result are present in
   the dom/ capture, and — from run.json driverActions, if recorded — how many
   interactions were needed to reach them.
5. The plan header's progress string, quoted verbatim, and the number of steps
   it names, versus the number of step rows present.

HOW TO DECIDE: The run whose plan block accounts for more of that run's own
record. Mismatch in either direction counts: a call that ran and is nowhere
visible, and a block that shows a call the record does not contain. If the plans
in both runs executed no tools at all, the path was not exercised in either run
— that is a `tie`. Do not decide on the quality or usefulness of the checklist
the model produced.

## PT2
----------------------------------------------------------------

THE QUESTION: Reading only the plan block after the cancel, what state does it
communicate to the reader, and does that match what actually happened?

MEASURE AND REPORT FOR BOTH RUNS:

1. From run.json driverActions: confirm a cancel was performed, and when. If a
   run has no cancel action recorded, say so — that run was not tested.
2. From dom/ or snapshots/: the pre-cancel and the post-cancel outerHTML of the
   plan block. Produce a list of every difference between them: which elements,
   labels, buttons and step-row texts changed, appeared, or disappeared. Quote
   the actual strings on both sides.
3. The exact text of every interactive control present in the POST-cancel block
   (button text or accessible name), and the count.
4. The exact text of every step row in the POST-cancel block, and the count.
5. What the assistant message text says after the cancel, quoted verbatim.
6. Then answer, per run, using only strings you have quoted: from the post-cancel
   block alone — with no memory of having clicked anything — what would a reader
   conclude about whether this plan is waiting on them, was abandoned, or has
   already run?

HOW TO DECIDE: The run whose post-cancel block communicates the state that
actually obtains. Note that losing information is also a failure: if a run's
post-cancel block no longer shows what was proposed, or no longer shows the step
list at all, report that against it — a reader cannot review a plan that has
been erased. If the pre/post difference is equivalent in both runs, that is a
tie.

## PT3
----------------------------------------------------------------

THE QUESTION: Does each plan block's account of what happened match what
happened — who stopped it, how far it got, and which steps never ran?

MEASURE AND REPORT FOR BOTH RUNS:

1. From run.json driverActions and timings.json: confirm a Stop was pressed
   while a step was executing, and at what point. If a run's stop did not land
   mid-plan — nothing was running, or everything had already finished — say so;
   that run was not tested and the comparison may not stand.
2. From dom/ or snapshots/: transcribe VERBATIM the plan header's progress
   string, and for every step row its glyph, its label text, and any class names
   that carry colour.
3. Per run, the counts: steps that completed, steps interrupted mid-execution,
   steps that never started.
4. Whether the header's progress number equals the number of rows that present
   as complete. Give both numbers.
5. For the interrupted step: quote its row text exactly, and report what the row
   attributes the halt to.
6. For the never-started steps: compare their rendering against a pre-execution
   snapshot of the same rows, if one exists. Report whether the strings are
   identical or differ, quoting both.

HOW TO DECIDE: The run whose block a reader could use to reconstruct what
actually happened. Over-statement counts as heavily as under-statement: a
progress count higher than the work done, or a row presenting as complete when
the record shows it was not, is as much a mismatch as a row that says nothing.
If the two blocks render equivalently, tie.

## FR1
----------------------------------------------------------------

THE QUESTION: From the message alone, can the reader tell what went wrong and
what to do next?

MEASURE AND REPORT FOR BOTH RUNS:

1. From fixtures/: confirm the shim served the seeded error frame, and quote the
   frame it served. If a run did not receive it, that run was not tested.
2. The length of the assistant message's visible text in reply.txt, and quote it
   in full if short or its first 200 characters if long. Report the number for
   both runs, including zero.
3. Compare reply.md against reply.txt: report whether anything the model emitted
   was lost in rendering, and what.
4. Quote whatever the message says about the cause of the failure. If nothing,
   write "nothing".
5. From dom/: every control present on that message, with its visible text or
   accessible name. Give the count and the names.
6. From timings.json / run.json: how long after the stream ended the composer
   input and send control became usable again. Give the number in ms for both
   runs.
7. Whether the user's own message is still present in transcript.json /
   messages-raw.json after the failure.

HOW TO DECIDE: The run that leaves the reader with more of (a cause, a clear
state, a way to proceed), all grounded in quotes. Check any stated cause against
the frame you quoted in step 1: a run that names a cause the served frame does
not support is worse, not better. If both messages are equivalent in content and
in available controls, tie.

## FR2
----------------------------------------------------------------

THE QUESTION: How long is the application unusable, and what does it tell the
reader while it is?

MEASURE AND REPORT FOR BOTH RUNS:

1. From fixtures/: confirm the stall server accepted the request and wrote
   nothing, in both runs. Quote the log line.
2. From timings.json and run.json driverActions, in ms from t0:
   - the first moment anything on screen addressed the situation — quote that
     text — or "never within the observation window";
   - the moment the composer and send control became usable again WITHOUT a Stop
     being pressed, or "never";
   - when Stop was pressed, if it was;
   - the state 2000 ms after Stop: was the composer enabled, and what did the
     assistant message say? Quote it.
   Give every one of these numbers for both runs.
3. Whether a Stop control was present and enabled throughout the wait, with the
   DOM evidence and its timestamps.
4. The assistant message's final visible text in each run, quoted.

HOW TO DECIDE: The run that returns control to the reader sooner AND accounts
for the silence — report both the timings and the text and weigh them together.
A run that ends the turn quickly but says nothing about why is not automatically
better than one that waits and then explains; report both properties before
deciding. If both runs behaved equivalently across the whole observation window,
tie.

## FR3
----------------------------------------------------------------

THE QUESTION: Does each application's summary of the review match the review it
actually received?

MEASURE AND REPORT FOR BOTH RUNS:

1. From fixtures/: confirm the review request was intercepted and what it was
   served. Quote the log line. If a run's review request was not intercepted,
   that run was not tested.
2. Quote, VERBATIM and IN FULL, the deliberation line each run displays — from
   reply.txt and from dom/. Note any difference between the two.
3. Report what that line asserts: does it name an outcome for the review, does
   it name a reviewer, does it state whether the draft was kept or changed?
4. The stored review content, if the artifacts contain it (transcript.json, or
   an expanded record in dom/): is it empty, and does the interface label it as
   such, or present an empty region under a heading that implies content? Quote
   what you find.
5. Whether the final answer text differs from any stored draft, if both are
   present.

HOW TO DECIDE: The run whose displayed summary is true of its own artifacts. A
line that asserts an outcome the artifacts cannot support fails — in EITHER
direction: claiming a completed review that did not complete, and equally
claiming a failure that did not occur. If both runs display the same string,
tie. Do not credit a run for a better-worded deliberation line; credit only
whether the line's claim is true of what the run recorded.
